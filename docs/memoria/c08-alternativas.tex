\chapter{Estudio de alternativas y viabilidad}
\label{cap:alternativas}
En este capítulo se argumentan las herramientas y tecnologías usadas en el proyecto, así como las
alternativas que se han considerado y por qué se ha optado por las elegidas. Se agruparán las
herramientas en tres secciones: \gls{backend}, \gls{frontend} y videojuego. Además se evaluará la
viabilidad económica y técnica del proyecto.

\section{Alternativas tecnológicas}
\label{c08:sec:alternativas-tecnologicas}

\subsection{Herramientas utilizadas en el backend}
\label{c08:subsec:herramientas-backend}
El \gls{backend} consiste en una API REST encargada de gestionar la lógica de negocio, el acceso a
datos y la comunicación con el \gls{frontend}.

\subsubsection{Python}
\label{c08:subsubsec:python}
Python es un lenguaje de programación de alto nivel, interpretado y multipropósito. Acorde a
la última encuesta a desarrolladores de Stack Overflow, es el tercer lenguaje más popular, después
de JavaScript y HTML/CSS (tecnologías que también se usan en este proyecto)
\parencite{encuestaTecnologias2024}. La ventaja de utilizar un lenguaje popular es que hay una gran
cantidad de herramienta, documentación y comunidad que pueden ayudar a resolver problemas y
mejorar la productividad del desarrollo. Se escoge Python frente a otros lenguaje como JavaScript o
Java porque es un lenguaje ya conocido por el autor y tiene una gran cantidad de bibliotecas
destinadas a la creación de APIs REST.

\subsubsection{FastAPI}
\label{c08:subsubsec:fastapi}
\tech{FastAPI}{https://fastapi.tiangolo.com/} es un \gls{framework} web para Python que permite crear
APIs REST de forma muy rápida y sencilla. Se basa en el estándar OpenAPI y permite generar documentación de
manera automática. Además, favorece la escritura de código limpio y mantenible, fomentando el uso de
la composición y la reutilización de código a través de su sistema de inyección de dependencias. %
Se escoge FastAPI frente a otros \glspl{framework} como Flask o Django por su simplicidad, rapidez
de desarrollo y libertad para estructurar el proyecto.

\subsubsection{PostgreSQL}
\label{c08:subsubsec:postgresql}
Para el almacenamiento de datos se ha optado por \tech{PostgreSQL}{https://www.postgresql.org/}, un
sistema de gestión de bases de datos relacionales de código abierto. Se escoge PostgreSQL frente a otros sistemas
de bases de datos por su robustez y escalabilidad. Además, es compatible con el estándar SQL,
estudiado en la asignatura de Bases de Datos, por lo que el autor ya tiene experiencia con él.

\subsubsection{SQLAlchemy}
\label{c08:subsubsec:sqlalchemy}
\tech{SQLAlchemy}{https://www.sqlalchemy.org/} es una librería de Python que proporciona un \gls{ORM}
para interactuar con bases de datos relacionales de forma sencilla. Permite definir modelos de datos
como clases de Python y realizar consultas a la base de datos utilizando una sintaxis muy similar a SQL, pero
con la ventaja de realizarse todo desde Python, utilizando sus tipos de datos y estructuras.

La alternativa a utilizar un \gls{ORM} sería realizar las consultas directamente a la base de datos
utilizando SQL, lo que puede ser más eficiente en algunos casos, pero también más propenso a errores
y menos mantenible. También supondría un problema de seguridad, puesto que las consultas directas a las
bases de datos son más propensas a sufrir ataques de inyección SQL, por lo que se debería prestar
especial atención a la validación de los datos introducidos por el usuario. Por último, realizar las
consultas directamente a la base de datos daría lugar a un código más acoplado y menos reutilizable:
cambiar la base de datos por otra distinta supondría tener que cambiar todas las consultas realizadas
en el código, mientras que utilizando un \gls{ORM} se puede cambiar la base de datos sin necesidad de
modificar el código, siempre que sea compatible con la herramienta escogida.

\subsection{Herramientas utilizadas en el frontend}
\label{c08:subsec:herramientas-frontend}
El \gls{frontend} consiste en una aplicación web que permite a los usuarios interactuar con el
\gls{backend} y el videojuego.

\subsubsection{TypeScript}
\label{c08:subsubsec:typescript}
JavaScript es el lenguaje de programación más utilizado en el desarrollo web
\parencite{encuestaTecnologias2024}, pero su tipado dinámico puede llevar a errores difíciles de
detectar y a un código menos legible y mantenible. TypeScript es un superconjunto de JavaScript que
añade tipado estático, eliminando muchos de estos problemas y mejorando la productividad del
desarrollo.

\subsubsection{React}
\label{c08:subsubsec:react}
\tech{React}{https://react.dev/} es una biblioteca de JavaScript para construir interfaces de usuario,
desarrollada por Facebook. Permite crear componentes reutilizables y gestionar el estado de la aplicación
de forma sencilla. Se escoge React frente a otras bibliotecas como Vue por su popularidad y mayor
flexibilidad, aunque su curva de aprendizaje pueda ser más pronunciada.

\subsubsection{Vite}
\label{c08:subsubsec:vite}
\tech{Vite}{https://vitejs.dev/} es una herramienta de construcción y desarrollo de aplicaciones web gratuita
y de código abierto que permite crear productos de manera rápida y sencilla. Inicialmente se
escogió NextJS como \gls{framework} para el \gls{frontend}, pero poco después de comenzar el
desarrollo se descartó, puesto que no permitía exportar la aplicación web como un sitio estático,
lo que era necesario para servir la aplicación de manera independiente del \gls{backend}. Esto
suponía tener que crear un servidor independiente para servir la aplicación, lo que parecía
innecesario para un proyecto de este tipo.

Se optó entonces por Vite como alternativa, ya que permite exportar la aplicación como un sitio web
estático y soporta TypeScript y React de forma nativa.

\subsubsection{MediaPipe BlazePose}
\label{c08:subsubsec:mediapipe}
BlazePose es un modelo de aprendizaje automático desarrollado por Google que permite detectar
poses humanas en tiempo real a partir de imágenes o vídeos \parencite{bazarevsky2020blazepose}
\parencite{xu2020ghum}. La decisión de utilizar BlazePose y no algún otro modelo de estimación de
posturas como OpenPose o PoseNet son varias. OpenPose es un modelo que destaca por su precisión y
capacidad para detectar múltiples personas en una imagen, pero es muy pesado y requiere una gran
cantidad de recursos, lo que lo hace inviable para este proyecto, puesto que se busca una solución
ligera y rápida que funcione en dispositivos móviles y navegadores web. Tanto PoseNet como BlazePose
son modelos diseñados para funcionar en dispositivos móviles y navegadores web, ambos son modelos
compatibles con TensorFlow.js. Aunque BlazePose resulta algo más preciso que PoseNet en la mayoría de
los casos \parencite{MediaPipeMirror}, se opta por BlazePose por su mejor combinación de velocidad,
precisión y tamaño del modelo. Además, BlazePose además de las coordenadas en 2D de las
articulaciones, también proporciona una estimación de la profundidad de las mismas, lo que puede
ser muy útil para mejorar la precisión de la detección de posturas en el videojuego.

\subsection{Herramientas utilizadas en el despliegue}
\label{c08:subsec:herramientas-despliegue}
\subsubsection{Docker}
\label{c08:subsubsec:docker}
Para el despliegue tanto del \gls{backend} como del \gls{frontend} se ha optado por \tech{Docker}
{https://www.docker.com/}, una herramienta de contenedorización que permite empaquetar aplicaciones
y sus dependencias en contenedores ligeros y portables. Esto permite distribuir la aplicación completa
en distintos equipos simplemente compartiendo el archivo de configuración y las fuentes del proyecto,
realizando la instalación y despliegue de forma automática.

Se escoge utilizar una herramienta de contenedorización para facilitar el despliegue en máquinas
distintas y evitar problemas de compatibilidad entre entornos. Se ha optado por Docker frente a
otras herramientas como \tech{Podman}{https://podman.io/} simplemente por su popularidad y porque
ya tenía experiencia previa con él.

\subsubsection{Caddy}
\label{c08:subsubsec:caddy}
\tech{Caddy}{https://caddyserver.com/} es un servidor web y proxy inverso que permite servir aplicaciones
web de forma sencilla y rápida con un simple archivo de configuración. Se escoge Caddy frente a otros
servidores web como Nginx o Apache por ser muy sencillo de configurar y por crear certificados
SSL de forma automática y gratuita, lo que permite servir la aplicación de forma segura sin
necesidad de comprar o generar un certificado.

\subsection{Herramientas utilizadas en el videojuego}
\label{c08:subsec:herramientas-videojuego}
Para el desarrollo del videojuego se ha optado por \tech{Unity}{https://unity.com/}, un motor de videojuegos
muy popular y versátil que permite crear juegos en 2D y 3D de forma sencilla. Unity utiliza el
lenguaje de programación C\# y cuenta con una gran cantidad de herramientas y recursos en línea que
facilitan el desarrollo de videojuegos. Se consideró Godot como alternativa, pero se descartó, puesto
que el motor aún se encuentra en desarrollo muy activo y suele sufrir cambios frecuentes que pueden
romper la compatibilidad con versiones anteriores. Por otro lado, Unreal Engine no soporta exportar
a WebGL \parencite{noWebExportUnrealReddit} \parencite{noWebExportUnreal}, lo que hace su uso
inviable para este proyecto. Por esto, y por la familiaridad del autor con Unity, se optó por este
motor para el desarrollo del videojuego.

\section{Viabilidad económica}
\label{c08:sec:viabilidad-economica}
\subsection{Costes}
El proyecto se ha desarrollado como parte de un trabajo académico, por lo que no se ha considerado
un presupuesto económico para su desarrollo. Por esto, se ha optado por utilizar herramientas y
tecnologías gratuitas y, en la medida de los posibles, de código abierto. El uso de herramientas
gratuitas y de código abierto permite reducir el coste del proyecto respecto a utilizar herramientas
de pago, pero también puede limitar las funcionalidades y el soporte disponible. Esto se puede
remediar utilizando herramientas más populares y con una comunidad activa que, aunque no ofrezcan
el servicio técnico que una herramienta de pago, sí que ofrecen una gran cantidad de documentación
y recursos en línea que pueden ayudar a resolver problemas y mejorar la productividad del
desarrollo.

Uno de los costes a tener en cuenta es el alojamiento del \gls{backend} y el \gls{frontend}, así
como del dominio. Actualmente, se está utilizando un servidor de Oracle Cloud gratuito para
albergar el proyecto, pero la máquina virtual no tiene las mejores prestaciones y puede
verse limitada en cuanto a recursos. Además, en el caso de que el proyecto se comercializase,
sería necesario adquirir más servidores para distribuir la carga de mejor manera, así como un
servidor dedicado para el almacenamiento de los datos del sistema.

Por ejemplo, si quisiéramos alojar el proyecto en un servidor de Google Cloud, el coste sería
de aproximadamente de 40\texteuro\ al mes por un servidor con 4 vCPUs, 16 GB de RAM y 10GB de disco
(con una permanencia de 3 años). A esto habría que sumarle el coste del almacenamiento de datos,
que serían unos 10\texteuro\ mensuales por 500 GB de almacenamiento en Google Cloud
\parencite{googleCloudPricing}.

Por otro lado, el dominio utilizado (\texttt{lueng.org}) es el dominio personal del autor,
por lo que no se ha considerado un coste para el proyecto. Sin embargo, si se quisiera utilizar
este como dominio del proyecto, habría que tener en cuenta el coste de renovación anual, que es
de aproximadamente $8.71$\texteuro\ .

Por último, cabe destacar que Unity, el motor de videojuegos utilizado, en su versión gratuita,
impone un límite de ingresos anuales de 200.000\texteuro\ para poder utilizarlo sin pagar una licencia
\parencite{unityPlans}. Si el proyecto superase este límite, sería necesario adquirir una licencia
de pago, lo que podría suponer un coste significativo.

\subsection{Comercialización}
Para comercializar el proyecto, se podría optar por un modelo de negocio basado en publicidad,
donde se mostrarían anuncios en la aplicación y el videojuego. Otra opción sería ofrecer el servicio
a cambio de una un pago único o una suscripción, que permitiría financiar el desarrollo del proyecto
y mantenerlo actualizado.
