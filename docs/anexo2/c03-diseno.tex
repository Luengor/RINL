\chapter{Diseño del sistema}
\label{anexo2:cap:diseno}
A partir del análisis del sistema, se puede proceder a su diseño. El diseño del sistema es una
representación más detallada de como se implementará el sistema, incluyendo la arquitectura,
los patrones de diseño utilizados, las tecnologías empleadas, etc., por lo que se puede considerar
una representación muy concreta de la solución planteada en el análisis \parencite{IBMDesignModel}.

Este capítulo se divide en varias secciones que describen los diferentes aspectos mencionados
anteriormente. En primer lugar, se presenta los patrones de diseño utilizados para
construir el sistema. A continuación se muestra el diagrama de clases, que representa todos los objetos
y sus relaciones en el sistema. Finalmente, se presenta la realización de los casos de uso (definidos
en el \primerAnexo) y el diagrama de despliegue, que muestra como se desplegará
el sistema en un entorno real.

\section{Patrones de diseño}
\label{anexo2:sec:patron-diseno}
En el diseño del sistema se han utilizado varios patrones de diseño de software. En esta sección se
describen los patrones utilizados y su justificación. Esto será de gran ayuda para entender la
estructura del sistema y el posterior diagrama de clases (\ref{anexo2:fig:diagrama-clases-diseno}).

\subsection{Cliente-servidor}
\label{anexo2:subsec:cliente-servidor}
El sistema está compuesto por cuatro componentes principales: la base de datos, una \gls{api} que
proporciona acceso a estos datos y a la lógica de negocio, el \gls{frontend} que proporciona una
página web para interactuar con el sistema y un videojuego desarrollado en Unity exportado a WebGL
y que se incluye en el \gls{frontend}.

El patrón de diseño arquitectónico escogido para el sistema es el patrón cliente-servidor. Este patrón
divide las tareas del sistema entre los proveedores de servicios (servidores) y aquellos que consumen
dichos servicios (clientes) \parencite{SunDistributedSystems}. En el caso de este sistema en concreto,
nos encontramos con un servidor que proporciona la funcionalidad de la lógica de negocio, otro servidor
encargado de realizar el acceso persistente a datos y un último que proporciona la interfaz de usuario
, que es consumida por los clientes a través de un navegador web. Esta separación en tres capas,
presentación, lógica de negocio y acceso a datos, se conoce como arquitectura en tres capas
\parencites{Ibm2025Apr}. Esta, permite desacoplar la estructura de los datos de la presentación de los
mismos, lo que facilita la evolución del sistema y la reutilización de los componentes
\parencite[p.~3]{nyabuto2024architectural}.

\subsection{Modelo Vista Controlador}
\label{anexo2:sec:mvc}
El patrón de diseño MVC se utiliza en la capa de presentación del sistema, en específico en las vistas
de React. Este patrón separa la lógica en tres componentes principales: el modelo, que representa los
datos del sistema y la lógica de negocio; la vista, que es la interfaz de usuario que muestra los datos
del modelo; y el controlador, que es el encargado de gestionar la interacción del usuario con la
vista y de actualizar el modelo en función de las acciones del usuario \parencite{NorfolkDevelopers2015Dec}.
Esta separación permite una mayor flexibilidad y reutilización del código, ya que cada componente
puede ser modificado o reemplazado sin afectar a lo demás, siempre que se mantenga la interfaz entre
ellos.

En el caso de este sistema, la vista está representada por los componentes de React, que son responsables
de mostrar los datos del modelo y de gestionar la interacción con el usuario. El controlador sería
el cliente encargado de realizar las peticiones al servidor, en este caso la clase \texttt{APIClient}
junto a los \textit{hooks} de React que se encargan de gestionar las peticiones y de actualizar
el estado de la aplicación\footnotemark. Por último, el modelo está representado por la API del
\gls{backend}, que proporciona los datos y la lógica de negocio del sistema. También se podría considerar
como parte del modelo al caché de datos que se almacena en el navegador del cliente, aunque se consideraría
como una fuente de verdad alternativa.

Así, cuando el usuario interactúa con la vista, esta envía las acciones al controlador, que a su vez
realiza las peticiones al servidor para alterar el modelo. Una vez el modelo ha sido actualizado, este
cambio se reflejará en la vista gracias a la reactividad de los componentes de React, completando la
comunicación triangular propia de MVC como se puede ver en la figura \ref{anexo2:fig:mvc}
\parencite{PatternOrientedSoftwareArchitecture}.

\subsection{\glsfirst{dao}}
\label{anexo2:sec:dao}
El servidor encargado de proporcionar las funcionalidades del sistema utiliza el patrón de diseño
\gls{dao} para acceder a los datos almacenados en la base de datos. Este patrón permite separar la lógica
de negocio del acceso a datos, lo que reduce el acoplamiento entre las diferentes capas del sistema y
facilita la modificación y mantenimiento de distintas secciones del sistema de manera independiente
\parencite{Zato2020Dao}.

\subsection{Inyección de dependencias}
\label{anexo2:sec:inyeccion-dependencias}
La inyección de dependencias es una técnica de programación en la que las dependencias de una clase
se proporcionan desde el exterior, en lugar de ser creadas por la propia clase
\parencite{DepInyectionStackOVerflow}. Esto no es patrón de diseño como tal, sino una técnica que
engloba a varios patrones de diseño como pueden ser la inyección de constructor, la inyección de
método o la inyección de propiedad por mencionar algunos. La inyección de dependencias permite
desacoplar las clases entre sí, permitiendo que una clase dependa de una interfaz en lugar de una
implementación concreta, lo que facilita la reutilización, el mantenimiento y la prueba de los
componentes individuales del sistema \parencite{Seemann2025Jun}.

En la aplicación, la inyección de dependencias se utiliza en el módulo del \gls{backend}, donde
las clases que implementan los \gls{dao} y los \textit{routers} de \texttt{FastAPI} reciben como
parámetro las dependencias que necesitan para funcionar, como por ejemplo la conexión a la base de
datos, funciones específicas de la aplicación como puede ser el envío de correos electrónicos o
otros datos como el actor actual del sistema. Esto facilita enormemente la prueba de las clases,
puesto que se pueden proporcionar implementaciones alternativas de las dependencias para realizar
las pruebas unitarias. En el caso propio de la aplicación, la dependencia a la base de datos se
reemplaza por una conexión a una base de datos SQLite local y la función de envío de correos
electrónicos se reemplaza por una función que simplemente imprime el correo electrónico en la
consola, evitando así el envío de correos electrónicos reales durante las pruebas.

Se puede ver un diagrama representando la inyección de dependencias para el envío de correos
electrónicos en la figura \ref{anexo2:fig:inyeccion-dependencias}.

\subsection{Singleton}
\label{anexo2:sec:singleton}
El patrón de diseño singleton se utiliza en Unity para garantizar que solo exista una instancia de
la clase \texttt{GameController} al mismo tiempo y exista un acceso global a ella. Esto permite
centralizar algunas de las funcionalidades comunes del videojuego evitando la creación de múltiples
instancias de la misma clase que podrían interferir entre sí y provocar comportamientos inesperados.
Este patrón es especialmente útil en el contexto de un videojuego, donde muchas veces es necesario
mantener un estado global que debe ser accesible desde diferentes partes del código como la configuración
actual del juego o el estado de las actividades \parencite{GameProgrammingPatterns}.

En esta aplicación, la clase \texttt{GameController} es la encargada de gestionar la configuración del
juego y de mantener referencias a objetos importantes de la escena, como pueden ser el visualizador de
posturas (\texttt{RINLBody}), el sistema de guiones para la escena (\texttt{SceneScript}) o el
comunicador con el \gls{backend} (\texttt{JSConnector}). Se puede ver un diagrama de este patrón para
el caso de la aplicación en la figura \ref{anexo2:fig:singleton}.

\section{Diagrama de clases}
\label{anexo2:sec:diagrama-clases-diseno}
El diagrama de clases de diseño, a diferencia del de análisis (\ref{anexo2:fig:modelo-dominio}), es
mucho más detallado, mostrando las clases tal y como se implementarán en el sistema, incluyendo
los atributos y métodos de cada clase, así como las relaciones entre ellas.

Se han distribuído las clases en cuatro paquetes, que representan distintas partes del sistema:
\begin{itemize}
    \item \textbf{Modelos de datos:} contiene las clases que representan los datos persistentes del
        sistema, en particular los usuarios, las actividades y las formas físicas. En la implementación
        real, estas clases se corresponden con las tablas de la base de datos y con las clases creadas
        por el \gls{orm}. En el caso de esta aplicación, se utiliza la biblioteca \texttt{SQLAlchemy}%
        \footnote{\url{https://docs.sqlalchemy.org/en/20/}} para gestionar la base de datos, por lo que
        estas clases heredan de la clase \texttt{Base} de \texttt{SQLAlchemy}.
    \item \textbf{Backend:} contiene las clases que implementan la lógica de negocio del sistema, incluyendo
        los controladores que gestionan las peticiones de los clientes y los sistemas que interactúan con
        la base de datos. Contiene tres subpaquetes:
        \begin{itemize}
            \item \textbf{Schemas:} contiene las clases que definen los esquemas de validación
                de los datos recibidos por el servidor, utilizando la librería \texttt{Pydantic}
                \footnote{\url{https://docs.pydantic.dev/latest/}}. Debido a esto, estas clases
                heredan de la clase \texttt{BaseModel} de \texttt{Pydantic}.
                Estas clases también son utilizadas por los \textit{routers} y los \textit{DAO}
                para realizar las operaciones de acceso a datos, desacoplando así la
                representación de los datos en la base de datos con la usada en el \gls{backend}.
            \item \textbf{DAO:} contiene las clases que implementan el patrón \gls{dao}, que
                se encargan de acceder a los datos almacenados en la base de datos.
            \item \textbf{Routers:} contiene las clases que implementan los \textit{routers} de
                \texttt{FastAPI}\footnote{\url{https://fastapi.tiangolo.com/}}, que son los encargados
                de gestionar las peticiones HTTP recibidas por el servidor y de invocar los métodos
                de los \textit{DAO} para acceder a los datos.
        \end{itemize}
    \item \textbf{React:} contiene las clases que implementan la interfaz de usuario del sistema,
        utilizando la biblioteca \texttt{React}\footnote{\url{https://react.dev/}}. Las clases
        contenidas en el subpaquete \texttt{components} son los componentes de \texttt{React}
        creados para la interfaz de usuario.
    \item \textbf{Unity:} contiene las clases principales del videojuego de Unity. Para la descripción
        en el diagrama, se han omitido los detalles de las clases existentes para jugar ambos minijuegos,
        centrándose en las clases que implementan la lógica principal de control y detección de posturas,
        puesto que son las que más complejidad estructural aportan al sistema.
\end{itemize}

Debido a la gran cantidad de clases que componen el sistema, se ha optado por dividir el diagrama
de clases en cuatro imágenes, una por cada paquete mencionado anteriormente (figuras
\ref{anexo2:fig:clases-modelos}, \ref{anexo2:fig:clases-backend},
 \ref{anexo2:fig:clases-react} y \ref{anexo2:fig:clases-unity}). En estos diagramas
las relaciones a clases de paquetes externos se muestran como dependencias al paquete, y no
como relaciones directas a las clases. Igualmente, se incluye una imagen que muestra
el diagrama completo, aunque es de difícil lectura debido a la gran cantidad de clases
y relaciones que contiene (figura \ref{anexo2:fig:diagrama-clases-diseno}), así como
una imagen que muestra únicamente los paquetes y sus relaciones
(figura \ref{anexo2:fig:paquetes-clases-diseno}). El diagrama de clases completo
también se encuentra disponible en el repositorio del proyecto%
\footnote{\url{https://github.com/Luengor/RINL/blob/fullapp/docs/anexo2/diagramas}}.

Hay varias cosas a destacar del diagrama de clases. En primer lugar, se puede observar que se
han utilizado dos estereotipos no estándar en los componentes de React y los \textit{routers} de
FastAPI. Estos estereotipos son \texttt{<<component>>} y \texttt{<<router>>} respectivamente. Estos
se han utilizado para indicar que estos elementos son componentes de la interfaz de react o son los
gestores de las peticiones HTTP del \gls{backend}. Se consideraba importante el uso de algún tipo
de estereotipo, puesto que estos objetos no son clases en el sentido estricto de la palabra. Los
componentes de React son funciones que devuelven \gls{tsx} (se ha utilizado la sección de
atributos de la clase para representar los argumentos que pueden tomar los componentes) mientras
que los \textit{routers} son sets de funciones agrupadas por rutas (de ahí que estas clases no
tengan parámetros).

Otro detalle importante es que se han omitido las relaciones entre los distintos componentes de
React y los \textit{routers} específicos de FastAPI, ya que estas relaciones son muy numerosas y
se consideró que no aportaban suficiente información al diagrama para justificar su inclusión. Para
incluir esta información de alguna manera, se ha relacionado la aplicación de React que contiene
todos los componentes con todos los Routers de FastAPI.

\section{Diagrama de despliegue}
\label{anexo2:sec:diagrama-despliegue}
En esta sección se presenta el diagrama de despliegue del sistema. Se compone de dos nodos: el
cliente, que accede al sistema a través de un navegador web, y el servidor (desplegado en
\url{https://rinl.soymilk.lueng.org/}) que proporciona el sistema al completo. Las distintas
partes que forman el sistema están contenidas en contenedores de Docker%
\footnote{\url{https://www.docker.com/}}, que permiten ejecutar el sistema de manera aislada y
realizar un despliegue sencillo y reproducible en cualquier entorno que soporte Docker. También
existe un proceso de Caddy\footnote{\url{https://caddyserver.com/}} que se encarga de
proporcionar el certificado SSL y de redirigir las peticiones al contenedor correspondiente
según la ruta de la petición.

Actualmente, el sistema se encuentra desplegado en un solo servidor, pero gracias a la división
de las distintas partes del sistema en contenedores, distribuir la aplicación entre distintos
hosts es una tarea sencilla: sería suficiente con desplegar los contenedores en los diferentes
equipos y configurar el \gls{frontend} y el \gls{backend} para que se comuniquen entre ellos
correctamente, así como configurar el proxy inverso de Caddy para que redirija las peticiones
a los lugares correctos.
