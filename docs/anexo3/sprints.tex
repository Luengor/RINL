\section{Sprint 1: Comunicación entre Unity y JavaScript}
\label{anexo3:sec:sprint1}

El primero de los sprints se centra en establecer la base del proyecto, buscando hacer funcionar la
detección de poses en Unity. Puesto que el acceso a la cámara en Unity a través de WebGL era algo
problemático, se decidió utilizar algún modelo de detección de poses para TensorFlow.js, y se optó por
MediaPipe BlazePose. Este se ejecutaría en JavaScript, de manera independiente de Unity, y se debería
comunicar con Unity de alguna manera.

La solución adoptada fue enviar mensajes desde JavaScript al objeto apropiado de Unity a través de
las funciones proporcionadas por Unity para WebGL. De esta manera, se podía enviar la información de los
\textit{landmarks} de la pose detectada a Unity, donde se procesaría para mostrar el cuerpo del usuario
en la escena.

Sin embargo, esta comunicación solo funcionaría si se exportaba el proyecto de Unity a WebGL, por lo
que era necesario hacer un export de Unity a WebGL y cargarlo en un servidor web cada vez que se quería
probar algo en Unity. Para facilitar el desarrollo, se optó por comunicar JavaScript y Unity a través de
un WebSocket, de manera que se pudiera enviar información en tiempo real entre ambos durante el desarrollo.

En cuanto a la planificación, este sprint tuvo pocos puntos de historia si se compara con los siguientes.
Esto se debe a que se trataba de un sprint principalmente exploratorio, donde se buscaba hacer funcionar
el sistema de detección de poses en Unity. Además, este sprint se realizó justo tras terminar la primera
convocatoria de exámenes de la carrera, por lo que los ánimos estaban bajos y no se esperaba que se
pudiese avanzar mucho. Es por esto que los próximos sprints tendrán una mayor carga de trabajo, ya con
una base sobre la que trabajar.

\section{Sprint 3: Desarrollo del primer minijuego y valoración de alternativas}
\label{anexo3:sec:sprint3}

Durante este sprint se buscó crear un minijuego sobre explotar globos, que sirviera como actividad
de prueba para el sistema. Además, se definieron los objetivos del sistema en tablas de objetivos
y se exploraron diferentes alternativas para la detección de poses. En particular, se probó OpenPose
y se exploró la posibilidad de utilizar solo los landmarks 2D que este modelo proporciona para la
detección de poses, en lugar de utilizar los landmarks 3D que se obtienen con MediaPipe. Finalmente,
se descartó esta última opción, ya que se consideró que la detección de poses en 3D era más conveniente
de cara a la creación de actividades en el futuro.

También se buscó la manera de enviar datos desde Unity a JavaScript para poder registrar las actividades
una vez sean completadas. Por último, se intentó situar la cámara en un \textit{overlay} para que no interfiriera
con el minijuego, pero se descartó esta opción, puesto que al jugar en pantalla completa, el elemento sería
ocultado.

El sprint se completó con éxito, siendo el primero en el que se completaron todas las tareas planificadas

\section{Sprint 6: Desarrollo del frontend y backend}
\label{anexo3:sec:sprint6}

utilizar Vite y Mantine en lugar de NextJS. Vite permite crear aplicaciones web que se pueden
exportar a una página estática, lo que facilita el despliegue del frontend. Mantine es una
biblioteca de componentes de React que permite crear aplicaciones web con un diseño atractivo y
moderno.

También se completó la base de datos, así como la API del backend, que permite gestionar usuarios,
actividades y formas físicas. Esta API se incluyó en un contenedor de Docker para facilitar su despliegue y
se realizaron pruebas unitarias con pytest para asegurar su correcto funcionamiento.
