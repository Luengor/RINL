\chapter{Plan de seguridad}
\label{anexo4:cap:seguridad}
En este capítulo se describen los aspectos de seguridad más relevantes para el correcto
funcionamiento de la aplicación. Se abordarán temas importantes para la seguridad de la aplicación,
como el almacenamiento de datos, el saneamiento de entradas, la autenticación y autorización, y
la seguridad de las conexiones. Además, se discutirán las medidas implementadas para garantizar la
protección de los datos y la privacidad de los usuarios.

\section{Almacenamiento de datos}
\label{anexo4:sec:almacenamiento}
Uno de los tipos de vulnerabilidad más comunes en aplicaciones web es la exposición de grandes
cantidades de datos sensibles sobre usuarios, como contraseñas, correos electrónicos, números de
teléfono, etc. Para evitar este tipo de problemas, es fundamental implementar medidas de seguridad
adecuadas en el almacenamiento de datos.

En el caso del despliegue actual de la aplicación, la base de datos no es accesible directamente desde
Internet, lo que reduce significativamente el riesgo de exposición de datos sensibles, al no ser posible
acceder a esta desde el exterior. Sin embargo, puesto que se puede acceder a la base de datos desde la
\gls{api} de la aplicación, es importante implementar medidas de seguridad adicionales para proteger
la información almacenada.

\subsection{Datos sensibles}
\label{anexo4:sec:datos-sensibles}
Tratándose de una aplicación que realiza un seguimiento de la forma física de los usuarios y recopila
datos como peso, altura, edad, etc., es crucial proteger la información sensible de los usuarios. Por
esto, ciertos campos de datos sensibles se almacenan en la base de datos de forma cifrada. Esto permite
que, incluso si un atacante logra acceder a la base de datos, no podrá obtener información sensible
sin las claves de cifrado adecuadas.

En la aplicación se utiliza el paquete \texttt{sqlalchemy\_utils} para el cifrado de datos sensible. Este
utiliza internamente el algoritmo de cifrado simétrico \texttt{AES-256} para cifrar los datos antes de
introducirlos en la base de datos y justo antes de devolverlos al usuario. El cifrado se realiza
utilizando una clave de cifrado que se almacena en el entorno de ejecución de la aplicación, lo que
garantiza que no se almacena en la base de datos ni en el código fuente de la aplicación.

También es importante destacar aquí que ni el video utilizado para la detección de posturas ni los
datos de las posturas detectadas se almacenan en la base de datos o transmiten fuera del cliente.
Estos datos se procesan directamente en el navegador del usuario y no se envían a la \gls{api} ni se almacenan
en ningún lugar.

\subsection{Contraseñas}
\label{anexo4:sec:contrasenas}
Para el almacenamiento de contraseñas, se utiliza el algoritmo de \gls{hash} \texttt{argon2}. Argon2 fue el
algoritmo ganador del concurso \textit{Password Hashing Competition} en 2015 y es ampliamente recomendado
por su seguridad y resistencia a ataques de fuerza bruta \parencite{OWASPPasswordStorage}. El algoritmo
permite ajustar tres parámetros: el tiempo de ejecución, la memoria utilizada y el nivel de paralelismo,
lo que permite adaptarlo a las capacidades del hardware y aumentar la seguridad. Se puede ver la configuración
utilizada en el listado \ref{anexo4:lst:argon2-config}.

\begin{lstlisting}[
    language=Python,
    caption={Configuración de \texttt{argon2} en la aplicación}, captionpos=b,
    label={anexo4:lst:argon2-config}]
from passlib.context import CryptContext

pwd_context = CryptContext(
    schemes = ["argon2"], deprecated = "auto",
    argon2__type = "ID",
    argon2__time_cost = 2,
    argon2__memory_cost = 19456,
    argon2__parallelism = 1
)
\end{lstlisting}

\subsection{Derecho al olvido}
\label{anexo4:sec:derecho-al-olvido}
El derecho al olvido (o derecho a la supresión) es un derecho que permite a los usuarios solicitar
la eliminación de sus datos personales de una aplicación o servicio \parencite{EuropeanParliament2016a}.
En la aplicación, se ha implementado una funcionalidad que permite a los usuarios eliminar su cuenta
y todos sus datos asociados (sus formas físicas y actividades realizadas) de forma permanente del
sistema.

\section{Saneamiento de entradas}
\label{anexo4:sec:saneamiento-entradas}
El saneamiento de entradas es una práctica de seguridad que consiste en validar y limpiar los datos
que recibe una aplicación para evitar diversos problemas. Si un actor malintencionado quisiera
atacar el sistema, uno de los primeros sitios por los que podría intentar hacerlo es a través
de las entradas que recibe la aplicación. Dos de los ataques más comunes que se pueden realizar
contra una aplicación web como la de este proyecto son el \gls{xss} y las inyecciones SQL.

El ataque de \gls{xss} consiste en inyectar código JavaScript malicioso en una página web para que
las víctimas lo ejecuten en su navegador con sus permisos. Normalmente, este tipo de ataques se realizan
estableciendo un campo público del sistema, como un comentario o el propio nombre del usuario con un
script que se ejecuta al cargar la página.

Sin embargo, en la aplicación desarrollada, no es posible consultar ningún dato introducido por otro usuario,
por lo que este tipo de ataques no son posibles. Además, si se muestra algún dato introducido por el usuario,
como su nombre, se hace de forma segura, puesto que los valores embebidos en archivos \gls{tsx} se escapan
automáticamente, evitando así la inyección de código JavaScript.

El otro tipo de ataque común es la inyección SQL, que consiste en inyectar código SQL malicioso en
una consulta SQL para manipular la base de datos de forma no autorizada. Para evitar este tipo de
ataques, la aplicación debería ser capaz de validar y limpiar las entradas que recibe antes de
procesarlas. En la solución desarrollada se utiliza el \gls{ORM} \texttt{SQLAlchemy}
\footnote{\url{https://www.sqlalchemy.org/}} para interactuar con la base de datos, lo que ayuda a
prevenir este tipo de ataques, ya que \texttt{SQLAlchemy} utiliza consultas parametrizadas para
evitar la inyección de código SQL malicioso.

Por último, otro aspecto importante a destacar es que, en la aplicación, se ha implementado
un sistema de validación de entradas que asegura que los datos introducidos por el usuario cumplen
con ciertos criterios antes de ser procesados. Esto se realiza con la ayuda de \texttt{Pydantic}%
\footnote{\url{https://docs.pydantic.dev/latest/}}, una biblioteca de validación de datos que
permite definir modelos de datos y validar las entradas de forma sencilla y eficiente. Gracias a
esta validación, se evita que se introduzcan datos cuyos tipos o formatos no sean los esperados,
lo que ayuda a prevenir errores y vulnerabilidades en la aplicación.

\section{Autenticación y autorización}
\label{anexo4:sec:autenticacion}
La autenticación y autorización son dos aspectos fundamentales para garantizar la seguridad de los
sistemas informáticos. La primera se encarga de verificar la identidad de un usuario, de confirmar
que es quien dice ser, mientras que la segunda se encarga de determinar que acciones puede realizar
ese usuario una vez se ha autenticado.

En esta aplicación, se utiliza un sistema de autenticación basado en tokens JWT para gestionar las
sesiones de usuario y otras funcionalidades relacionadas con la seguridad. Por otro lado, en
cuanto a la autorización, en la aplicación no existen diferentes roles de usuario, solo se
distingue entre usuarios que hayan verificado su correo electrónico y aquellos que no lo han hecho.

\subsection{JWT}
\label{anexo4:sec:jwt}
El sistema de autenticación de la aplicación se basa en el uso de tokens JWT (JSON Web Tokens).
Un token JWT es una forma compacta y segura de representar y transmitir información entre dos
partes. Estos tokens contienen una serie de afirmaciones (claims) que pueden ser verificadas y
firmadas digitalmente, lo que garantiza la integridad y autenticidad de la información contenida
en ellos \parencite{rfc7519}.

En la aplicación se usan tokens para varias labores, como la autenticación de usuarios, la
verificación de correos electrónicos y la actualización de estos. El procedimiento que se sigue
para el caso de la autenticación de usuarios es el siguiente:
\begin{enumerate}
    \item El usuario envía sus credenciales (correo electrónico y contraseña) a la \gls{api}.
    \item La \gls{api} verifica las credenciales y, si son correctas, genera un token JWT que contiene
          el identificador del usuario y la fecha de expiración del token. Este token se firma
          con una clave secreta que solo la \gls{api} conoce para poder verificar su autenticidad.
    \item El usuario recibe el token y lo almacena en su cliente.
    \item En cada solicitud posterior a la \gls{api}, el usuario incluye el token en el encabezado de
          autorización de la solicitud.
    \item La \gls{api} verifica el token, comprobando su firma y asegurándose de que no ha expirado. Si
          el token es válido, la \gls{api} permite el acceso a los recursos solicitados. Si no, responde
          con un error de autenticación.
\end{enumerate}

El mayor riesgo de seguridad asociado al uso de tokens JWT es el robo del token por parte de un
atacante. Para que un ataque de este tipo tenga éxito, el atacante debe conseguir acceder al token
del usuario antes de que este expire (en la aplicación, el tiempo de expiración de \textit{todos}
los tokens es solo de 15 minutos). Es un riesgo que se mitiga utilizando HTTPS para cifrar las
comunicaciones entre el cliente y la \gls{api} y teniendo en cuenta que, el almacenamiento de los tokens
en el cliente, es privado para cada sitio web.

Las maneras en las que un atacante podría robar un token se limitarían entonces a impersonar la
página web de la aplicación para robar el usuario y contraseña y obtener ellos mismos el token, o
ganar acceso al dispositivo del usuario para robar el token directamente.

\subsection{Verificación}
\label{anexo4:sec:verificacion}
Para hacer uso de la mayoría de las funcionalidades de la aplicación es necesario que el usuario
verifique su correo electrónico. Para ello, se envía un correo electrónico al usuario con un
enlace para verificarlo. Cabe destacar que, para poder utilizar dicho enlace, el usuario debe
haber iniciado sesión en la aplicación, evitando así que el receptor incorrecto de un correo
de verificación pueda hacer uso de él.

Esta obligación de verificación es una medida de seguridad que ayuda a prevenir el registro de
cuentas falsas o spam, evitando que usuarios malintencionados puedan crear cuentas con correos
que no les pertenecen.

\section{Seguridad de las conexiones}
\label{anexo4:sec:conexiones}
Otro aspecto importante de la seguridad de la aplicación es la protección de las conexiones entre
el cliente y el servidor. Para ello, se utilizan varias medidas de seguridad que garantizan la
confidencialidad e integridad de los datos transmitidos.

\subsection{HTTPS}
\label{anexo4:sec:conexiones-https}
Para proteger las conexiones entre el cliente y el servidor, se utiliza HTTPS, que cifra las
comunicaciones entre el cliente y el servidor utilizando TLS (Transport Layer Security). Esto
garantiza que los datos transmitidos entre el cliente y el servidor no puedan ser interceptados ni
modificados por terceros durante su tránsito. Así, ataques como el robo de credenciales o el
acceso a datos sensibles se vuelven mucho más difíciles de llevar a cabo.

La elección de utilizar la versión segura de HTTP fue, en realidad, completamente obligatoria, puesto
que el uso de la cámara web y el micrófono del dispositivo del usuario requiere que la conexión sea
segura en todos los navegadores modernos \parencite{MDNGetUserMedia}.

\subsection{CORS}
\label{anexo4:sec:conexiones-cors}
El uso de CORS (Cross-Origin Resource Sharing) es una medida de seguridad que permite a los
navegadores web controlar el acceso a recursos de diferentes orígenes. En la \gls{api} de la aplicación,
se ha configurado CORS para permitir el acceso solo desde el origen correcto
(\url{https://rinl.soymilk.lueng.org}) y para permitir el uso de los métodos HTTP necesarios para la
interacción con la \gls{api}.

Cabe destacar que CORS es solo una medida de seguridad del lado del cliente, es decir, su navegador
deberá cumplir con las restricciones de CORS para acceder a la \gls{api}. Esto no significa que la \gls{api}
deniegue el acceso a otros orígenes, sino que los navegadores no realizarán las solicitudes a menos
que su origen esté permitido. Por lo tanto, es importante tener en cuenta que CORS no es una
solución de seguridad completa, sino una medida adicional para proteger la aplicación de ataques
de tipo \gls{xss} y \gls{csrf}.

\begin{lstlisting}[
    language=Python,
    caption={Configuración de CORS en la \gls{api}}, captionpos=b,
    label={anexo4:lst:cors-config}]
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from backend.core.common import FRONTEND_URL

app = FastAPI(
    title="RINL",
    root_path="/api",
)

app.add_middleware(
    CORSMiddleware,
    allow_origins=[FRONTEND_URL],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT",
                   "DELETE", "OPTIONS"],
    allow_headers=["*"],
)
\end{lstlisting}

\section{Pruebas unitarias}
\label{anexo4:sec:pruebas}
Se conoce como prueba unitaria a un test que se realiza sobre una unidad de código, sobre la
cantidad más pequeña de código que se puede probar de forma aislada. Para la aplicación
desarrollada, se ha utilizado el framework de pruebas \texttt{pytest}
\footnote{\url{https://docs.pytest.org/en/stable/}} para implementar las pruebas unitarias.

Aunque las pruebas unitarias no son una medida de seguridad en sí mismas, son una herramienta
importante para garantizar la ausencia de errores y, por tanto, de vulnerabilidades en la
aplicación. Algunos de los tests unitarios implementados en la aplicación consisten en realizar
acciones que deberían fallar si la aplicación no se comporta de forma segura, como intentar
acceder a datos sensibles sin la autenticación adecuada o intentar realizar acciones no autorizadas.

\begin{lstlisting}[
    language=Python,
    caption={Test unitario de actualización de usuario no verificado}, captionpos=b,
    label={anexo4:lst:test-update-unverified-user}]
def test_update_unverified_user(
        client: TestClient,
        unverified_login_token: str):
    # Update user
    response = client.put(
        "/user/me",
        headers = {
            "Authorization": f"Bearer {unverified_login_token}"
        },
        json={
            "email": "test2",
            "name": "test2",
            "year_of_birth": 2001,
        },
    )

    # Check response
    assert response.status_code == 400
    assert response.json()["detail"] == NOT_VERIFIED.detail
\end{lstlisting}
